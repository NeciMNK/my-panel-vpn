## 1. Что это за проект

Личная VPN-панель: интерфейс и ядро [3x-ui](https://github.com/MHSanaei/3x-ui)
(Go + React, управляет Xray-core) плюс модель «мастер + ноды» в духе
Remnawave. Один мастер хранит пользователей и настройки, ноды (другие
инстансы панели) только обслуживают трафик и получают конфиг с мастера.

Цели владельца:

- все протоколы Xray (VLESS/Reality, VMess, Trojan, SS-2022, Hysteria2, TUIC,
  WireGuard, AmneziaWG, MTProto) из одной панели;
- ноды добавляются одной командой, настраиваются только с мастера;
- каскады «вход → выход» в два клика, балансировка по скорости внутри страны,
  удержание выхода (IP) 15 минут;
- минимальная и максимальная скорость на пользователя;
- доступ пользователей к домашней сети по правилам «кто → какая подсеть/IP»;
- WARP одним переключателем;
- 2–3 мастера с автоматическим переключением и возвратом главенства;
- оплата и продление через Telegram-бота, удобная страница подписки;
- в будущем — собственная панель, не зависящая от кода 3x-ui (раздел 8).

Проект личный, используется владельцем, репозиторий публичный.

## 2. Стек и устройство

| Часть | Технологии |
| --- | --- |
| Бэкенд | Go 1.27, Gin, GORM; модуль `github.com/mhsanaei/3x-ui/v3` (оставлен, чтобы чисто подтягивать апстрим) |
| БД | PostgreSQL (основная для форка, `XUI_DB_TYPE=postgres`, `XUI_DB_DSN=...`), SQLite по умолчанию у апстрима |
| Прокси-ядро | Xray-core как дочерний процесс + его Go-пакеты для конфигов и gRPC API |
| Доп. процессы | `mtg-multi` (MTProto), встроенные TUIC и AmneziaWG на Go |
| Фронтенд | React 19 + Ant Design 6 + Vite 8 + TypeScript, собирается в `internal/web/dist/` и встраивается в бинарник |
| Документация | `docs/` — отдельный сайт Next.js/Fumadocs (pnpm) |

Ключевые идеи (подробно в `docs/architecture.md`):

- **БД → конфиг Xray.** Inbound'ы и клиенты лежат в БД, при изменении конфиг
  пересобирается и применяется «горячо» через gRPC API Xray, перезапуск — только
  когда иначе нельзя.
- **`runtime.Runtime`.** Любая операция, меняющая inbound/клиента, идёт через
  интерфейс `Local` (своя Xray) или `Remote` (нода по HTTPS/mTLS). Прямой вызов
  `internal/xray/api.go` из контроллера или cron-задачи ломает мультинодовую
  схему, хотя все локальные тесты проходят.
- **Сервер подписок** (`internal/sub/`) — отдельный HTTP-сервер для клиентов
  (raw / JSON / Clash).

Где что лежит (новое в форке отмечено ★):

| Путь | Назначение |
| --- | --- |
| `main.go` | точка входа и CLI `x-ui` (в т. ч. ★ `x-ui cluster ...`) |
| `internal/database/` | модели GORM, миграции в `db.go` |
| `internal/xray/` | процесс Xray, генерация конфига, gRPC API |
| `internal/web/controller/` | REST API панели |
| `internal/web/service/` | бизнес-логика; ★ `cascade*.go`, `sub_balancer.go`, `speed.go`, `home_network.go`, `warp_switch.go`, `master_cluster.go`, `managed_template.go`, `node_join.go`, `billing.go`, `ledger.go`, `migration*.go`, `panel_proxy.go`, `tg_vpn_fallback.go`, `tlscert/` |
| `internal/web/job/` | cron-задачи (трафик, синк нод, лимиты и т. д.) |
| `internal/web/runtime/` | Local/Remote, связь мастер–нода по mTLS |
| ★ `internal/nodejoin/` | установка ноды одной командой (`install-node.sh`, бандл) |
| ★ `internal/homenet/` | туннели домашней сети (WireGuard / OpenVPN / L2TP / IKEv2) |
| ★ `internal/shaper/` | ограничение скорости через `tc` |
| ★ `internal/acme/` | выпуск Let's Encrypt через Cloudflare DNS |
| `internal/sub/` | подписки |
| `frontend/src/pages/nodes/` | ★ страницы «Ноды», «Каскады», «Домашние сети», «WARP», «Мастеры», «Ограничения скорости»; `pages/ledger/` — «Финансы»; `pages/sub/` — страница подписки |
| `tools/openapigen/` | генерация типов и OpenAPI из Go-структур |

★ — код форка, в `main` с PR #1 и следующих (см. раздел 3).

## 4. Дорожная карта форка (подробно)

Форк — рабочая панель на ближайшие месяцы, пока своя панель (раздел 8) не
догонит его. Поэтому сначала доводим форк до стабильной работы на проде, а уже
потом вкладываемся в новую панель. Каждая задача ниже — отдельный PR в `main`,
если не сказано иначе. Оценки даны в рабочих днях одного человека или одной
ИИ-сессии с проверкой человеком; это ориентир, а не обещание.

### 4.1. Слить открытые PR — сделано (10–11.11.2026)

Все PR первоначального плана (#1, #10, #11, #13, #14, #15, #17, #19) и
доработки к ним слиты, `main` собирается. Новые PR сливаются так же: по одному,
обновляя ветку от свежего `main` (merge, не rebase) и прогоняя `make verify`.
Конфликты обычно в `internal/web/translation/*.json`,
`frontend/src/pages/api-docs/endpoints.ts`, `frontend/public/openapi.json`,
`docs/public/openapi.json` и миграциях `internal/database/db.go`.
Сгенерированные файлы не править руками: взять любую сторону и
перегенерировать `make gen` и `cd docs && pnpm gen:api`. В миграциях сохранить
обе стороны в порядке слияния.

### 4.2. Проверка на тестовом стенде (идёт)

Ставится сборка из `main` на тестовый мастер и тестовую ноду (раздел 5).
Каждый сценарий записывается в issue «Проверка на стенде: <функция>» с
результатом. Найденная ошибка — отдельный `fix(...)` PR с тестом, который
воспроизводит её без стенда, если это возможно.

| Функция | Сценарий проверки | Что считаем успехом |
| --- | --- | --- |
| Нода одной командой | на мастере «Добавить ноду» → команда на чистом контейнере | нода появляется в списке онлайн за 2–3 минуты без ручного ввода адреса и токена, страна определена |
| Шаблон Xray с мастера | изменить outbound и правило в шаблоне ноды, сохранить | конфиг на ноде обновился, активные соединения не оборвались (если правка позволяет горячее применение) |
| Каскад | вход = тестовый мастер, выход = тестовая нода; подключиться клиентом | внешний IP клиента = IP выхода; пользователь в подписке видит только вход |
| Балансир по стране | два выхода одной страны, один «замедлить» через `tc` | новые подключения уходят на быстрый выход, в подписке есть запись «страна (авто)» |
| Удержание выхода 15 мин | подключиться через «авто», оборвать сеть на 5 минут, вернуться | IP выхода тот же; после 15+ минут офлайна закрепление снимается |
| Ручной выбор сервера | после «авто» выбрать в клиенте конкретный сервер | закрепление сбрасывается, трафик идёт через выбранный сервер |
| Макс. скорость | лимит 5 Мбит/с пользователю, замер speedtest | скорость в пределах лимита ±10 %, другие пользователи не задеты |
| Мин. скорость | порог выше, чем может дать выход | новые подключения идут на другой выход; если его нет — одно уведомление в Telegram за 30 минут |
| Домашняя сеть WireGuard | туннель до тестового роутера/контейнера, правило «пользователь → одна подсеть» | разрешённая подсеть доступна, соседняя подсеть и другие пользователи — нет |
| Домашняя сеть OpenVPN, L2TP/IPsec | то же через системный клиент на ноде | туннель поднимается после перезагрузки ноды сам |
| WARP | переключатель «весь трафик», затем «только выбранные сайты» | IP на проверочном сайте — Cloudflare; в режиме сайтов остальной трафик идёт напрямую |
| Несколько мастеров | 2 мастера + свидетель по инструкции `FORK.ru.md`, выключить главный | через ~20 с ведущим стал запасной, пришло уведомление; после возврата главного через ~30 с главенство вернулось |
| Сертификаты | выпуск на тестовом домене через Cloudflare DNS | сертификат выпущен, продление по расписанию отрабатывает (проверить сдвигом даты или staging-сервером LE) |
| Миграция | импорт из копии рабочей базы 3x-ui и из Remnawave (только чтение) | ссылки подписок пользователей не изменились, клиенты подключаются без перенастройки |
| Бот с оплатой | тестовый пользователь проходит оплату, продление, «оплачу позже» | сроки продлены верно, повторная отсрочка раньше 30 дней запрещена |
| Прокси панели | «Через мой VPN» с клиентом на ноде | исходящие запросы панели (обновления, геобазы, Telegram) идут через VPN |

Готово, когда: все строки таблицы проверены, у каждой есть issue с итогом,
ошибки исправлены или записаны как известные ограничения в раздел 3.

### 4.3. Переезд на прод (1–2 дня, только с разрешения владельца)

1. Резервная копия текущей базы и конфигов прода (и проверка, что она
   восстанавливается на тестовом мастере).
2. Перенос по одной ноде: нода переводится на сборку форка, проверяется,
   только потом следующая.
3. План отката: старая сборка и копия базы лежат рядом, откат — одна команда.
4. Сутки наблюдения: трафик считается, ноды онлайн, ошибок в логах нет.

| 6 | Журнал действий администратора (кто, что, когда изменил) | разбор ошибок, особенно когда в проекте несколько людей | 2 дня |

| 8 | Регулярное подтягивание апстрима 3x-ui раз в 1–2 недели: `git merge upstream/main`, `make verify`, PR `chore(upstream): merge 3x-ui <дата>` | исправления безопасности и Xray | 0,5 дня за раз |

Пункты 1–8 не зависят друг от друга, кроме 7 (лучше после 3). Новые идеи
добавлять в эту таблицу в том же PR, где их начинают делать, или через issue.

### 4.5. Что в форке делать не будем

- Глубокий рефакторинг кода апстрима: он мешает подтягивать 3x-ui, а
  замена ему — своя панель.
- Смена модуля Go и переименование пакетов.
- Функции, которые нужны только для продажи панели другим (мультиарендность,
  реселлеры) — это задача своей панели, если вообще понадобится.

## 6. Правила работы

Полный список — в `CLAUDE.md`. Самое важное:

- **Ветки и PR.** Одна задача — одна ветка — один PR в `main`. Прямые пуши в
  `main` запрещены. Назначать `NeciMNK` исполнителем PR (ревьюером назначить
  нельзя, если PR создан от его имени).
- **Коммиты** — conventional: `type(area): короткое повелительное описание`,
  в теле — зачем. Типы: `fix`, `feat`, `chore`, `refactor`, `perf`, `docs`,
  `style`. Рефакторинг отдельно от фич.
- **TDD.** Баг → сначала тест, который падает по описанной причине, потом
  исправление. Фейковые тесты (геттеры, пересчёт той же формулой, слабые
  проверки вроде `err != nil`, перегенерированные снимки) запрещены.
- **Правильное исправление, а не маленькое.** Ищите корень проблемы; заплатки,
  скрывающие симптом, не принимаются.
- **Слои.** Изменение inbound/клиента — только через `runtime.Runtime`.
  Изменение модели БД — только с миграцией в `internal/database/db.go`.
- **API.** Новый маршрут в `internal/web/controller/` → запись в
  `frontend/src/pages/api-docs/endpoints.ts` → `make gen` → копия
  `frontend/public/openapi.json` в `docs/public/` → `cd docs && pnpm gen:api`.
- **i18n.** Новый ключ — во все 14 файлов `internal/web/translation/` и сразу
  используется в коде. Интерфейс форка — русский и английский, остальные
  локали можно заполнять английским текстом.
- **Комментарии в коде** — не длиннее 2 строк, объясняют «почему», а не «что».
- **Язык.** Код, коммиты и комментарии — по-английски; документы для владельца
  (`plan.md`, `FORK.ru.md`) и описания PR — по-русски.

### Как работать ИИ-агенту

1. Прочитать `plan.md`, `CLAUDE.md`, нужный раздел `docs/architecture.md`.
2. Взять задачу из раздела 4 (или из issue), создать ветку `<agent>/<кратко>`.
3. Писать тест → код → `make verify` (и `make race`/Postgres/node-e2e, если
   задеты БД, ноды или синхронизация).
4. Открыть PR по шаблону `.github/pull_request_template.md`, по-русски
   описать что и зачем, указать, что проверено, а что нет.
5. Обновить таблицы состояния в разделе 3 этого файла в том же PR.
6. Не делать необратимых действий (прод-серверы, удаление данных, публикация
   секретов) без явного разрешения владельца.

## 7. Лицензия: что можно и чего нельзя

Код 3x-ui распространяется по **GPL-3.0**. Всё, что сделано в этом
репозитории поверх него (включая новые файлы форка, которые вызывают код
3x-ui и собираются с ним в один бинарник), — производная работа и тоже
распространяется только по GPL-3.0. Сменить лицензию этого репозитория
нельзя: на код апстрима у нас нет прав, а его авторов сотни.

Что GPL-3.0 реально требует:

- при передаче бинарника кому-либо — дать и исходники под той же лицензией;
- сохранять `LICENSE`, указания авторства и отметку об изменениях (`NOTICE.md`).

Чего GPL-3.0 **не** требует: публиковать код, если панель используется только
самим владельцем или как сетевой сервис (это не AGPL); не запрещает платные
подписки для пользователей VPN. Для личного проекта лицензия почти ничем не
мешает. Уходить от неё имеет смысл, только если нужна закрытая или другая
лицензия (продажа панели, закрытый код).

Почему нельзя «просто переписать файлы» здесь же: переименование, перенос в
другой репозиторий, переформатирование или переписывание функций по одной,
глядя на оригинал, оставляют работу производной. Уйти от GPL можно только
**чистой реализацией (clean room)**: новый код пишется с нуля по спецификации
поведения, без копирования и без построчного пересказа кода 3x-ui. Идеи,
протоколы, форматы ссылок и подписок, API Xray авторским правом не защищены —
их можно повторять.

Код Remnawave (AGPL-3.0) и других панелей (Marzban, Marzneshin, Hiddify и т. п.)
не копировать ни в форк, ни в новую панель — только идеи.

Это не юридическая консультация. Перед выпуском своей панели под другой
лицензией стоит показать этот раздел и историю разработки юристу.

## 8. Путь к собственной независимой панели

Цель: отдельный проект с собственной лицензией (выбирает владелец: MIT,
Apache-2.0 или закрытая), в котором нет кода 3x-ui. Форк продолжает работать,
пока новая панель не догонит его по нужным функциям, затем пользователи
переносятся миграцией без смены ссылок подписок.

Масштаб: в форке около 110 тыс. строк Go (без тестов) и около 120 тыс. строк
TypeScript. Переписывать один в один не нужно: новая панель делается под наши
сценарии (мастер + ноды, PostgreSQL, Linux), без наследия SQLite, Windows и
редких функций апстрима. Реалистичный объём первой рабочей версии — в 3–5 раз
меньше форка.

### 8.1. Правила чистой реализации

1. **Отдельный репозиторий** (рабочее имя `NeciMNK/<новое имя>`), новый
   Go-модуль, своя структура пакетов, своя схема БД, свой `LICENSE` с первого
   коммита. Форк не подключается ни как зависимость, ни как git-подмодуль, ни
   как `upstream`.
2. **Две роли.**
   - «Аналитик» может читать код форка и работать с живой панелью. Он пишет
     спецификации поведения в `spec/` нового репозитория: что делает функция,
     входы и выходы, форматы, граничные случаи, примеры запросов и ответов.
     Без кода, без псевдокода, повторяющего структуру функций 3x-ui, и без имён
     внутренних функций, типов и переменных 3x-ui.
   - «Разработчик» пишет код только по спецификациям, официальной документации
     Xray-core и открытым стандартам и **не открывает** исходники 3x-ui и форка.
   Один человек не должен быть в обеих ролях для одного модуля.
3. **ИИ-агенты.** Агент-разработчик запускается в окружении, где подключён
   только новый репозиторий (в облачной сессии — без репозитория форка), в
   промпт не вставляются куски кода 3x-ui и форка. Спецификации пишет отдельная
   сессия-«аналитик». Это записывается в описании PR.
4. **Журнал происхождения.** В каждом PR нового репозитория раздел
   «Источники»: по каким файлам `spec/` и внешним документам написан код.
   Это доказательство независимости, если вопрос когда-нибудь возникнет.
5. **Зависимости** проверяются по лицензии до добавления: Xray-core (MPL-2.0)
   допустим и как Go-библиотека, и как отдельный бинарник (изменённые файлы
   самого Xray остаются под MPL); MIT, Apache-2.0, BSD, ISC — свободно;
   GPL/AGPL-библиотеки в бинарник новой панели не тянуть. Геобазы (GPL-3.0)
   скачиваются как отдельные файлы данных и не встраиваются. В CI добавляется
   проверка лицензий зависимостей (например, `go-licenses` и `license-checker`
   для npm).
6. **Наш код из форка** тоже не переносится копированием: он вырос внутри
   кода 3x-ui и вызывает его. Его поведение описывается в спецификации и
   реализуется заново, как и всё остальное.
7. **Что можно брать свободно:** идеи и сценарии, форматы ссылок
   (`vless://`, `trojan://`, `ss://`, `hysteria2://` и т. п.), форматы подписок
   (base64, JSON Xray, Clash/Mihomo, sing-box), API и формат конфига Xray,
   протоколы, публичный REST API других панелей для миграции.

### 8.2. Предлагаемая архитектура новой панели

Это стартовое предложение, финально утверждается в этапе A.

| Часть | Решение | Почему |
| --- | --- | --- |
| Язык бэкенда | Go | тот же стек, Xray-core на Go, один статический бинарник |
| Процессы | `panel` (мастер: API, UI, подписки, фоновые задачи) и `agent` (нода: Xray и туннели) — два отдельных бинарника | нода лёгкая и без БД; мастер не обслуживает трафик пользователей |
| БД | только PostgreSQL; миграции — нумерованные SQL-файлы (например, `goose`), доступ — `pgx` + сгенерированные запросы (`sqlc`) | одна СУБД, явная схема, без ORM-магии |
| API | OpenAPI-first: схема `api/openapi.yaml` → генерация сервера и клиента TypeScript | контракт один, фронтенд и сторонние клиенты не расходятся с бэкендом |
| Связь мастер–нода | gRPC поверх mTLS, нода подключается к мастеру сама (исходящее соединение) | ноде не нужен открытый порт управления, проще NAT и фаерволы |
| Модель синхронизации | «желаемое состояние»: мастер вычисляет полный конфиг ноды с номером версии, агент применяет и сообщает фактическую версию и здоровье | после обрыва связи нода сама догоняет последнюю версию, нет потерянных событий |
| Xray на ноде | отдельный процесс Xray, управление через его gRPC API (пользователи, правила) с перезапуском только при смене inbound'ов | горячее добавление пользователей без обрыва соединений |
| Учёт трафика | агент раз в N секунд отдаёт счётчики по пользователям, мастер пишет агрегаты; идемпотентно по номеру отчёта | повтор отчёта после обрыва не удваивает трафик |
| Фронтенд | React + TypeScript + Vite, UI-библиотека с лицензией MIT (например, Ant Design), своя структура страниц | знакомый стек, лицензия совместима |
| Подписки | отдельный HTTP-обработчик на мастере (или отдельный домен), кэш по версии данных пользователя | быстро, не зависит от нагрузки на админку |
| Несколько мастеров | ведущий выбирается по приоритету через блокировку в PostgreSQL, база — Patroni | та же схема, что в форке, но спроектированная с первого дня |
| Конфигурация | переменные окружения + файл, без настроек «в коде» | проще разворачивать и документировать |
| Наблюдаемость | метрики Prometheus, структурные логи JSON | стандартные инструменты вместо своих графиков на первом этапе |

Основные сущности модели данных (уточняются в `spec/data-model.md`):

- **Admin** — администратор, роли (владелец, оператор, только чтение), 2FA.
- **User** — пользователь VPN: срок, лимит трафика, лимиты скорости, статус,
  группы, токен подписки, привязка к Telegram.
- **Plan** — тариф: цена, срок, трафик, лимиты, доступные серверы.
- **Payment** — оплата и продления, ссылки на тариф и пользователя.
- **Node** — сервер: адрес, страна, состояние, версия агента, версия конфига.
- **Inbound** — точка входа на ноде: протокол, порт, транспорт, TLS/Reality.
- **Host** — как вход показывается в подписке (адрес, имя, порядок).
- **Cascade** — связка «вход → выходы», балансировка, удержание выхода.
- **HomeNetwork** + **AccessRule** — домашние сети, подсети, IP и правила доступа.
- **Squad/Group** — группа пользователей с общим набором входов и правил.
- **TrafficStat** — агрегированный трафик по пользователю, ноде и времени.
- **AuditLog** — журнал действий администраторов.

### 8.3. Этапы, задачи и критерии готовности

Оценки — рабочие дни одного разработчика (или ИИ-сессии с проверкой
человеком). Итого до переезда — ориентировочно 3–5 месяцев неполной занятости.

#### Этап A. Спецификации (2–3 недели)

Выполняет «аналитик». Результат — папка `spec/` в новом репозитории.

| Файл | Содержание |
| --- | --- |
| `spec/README.md` | цели, границы (что не делаем), словарь терминов |
| `spec/data-model.md` | сущности из 8.2, поля, связи, ограничения, что удаляется каскадно |
| `spec/api.md` + `api/openapi.yaml` | все операции админки: методы, поля, ошибки, права |
| `spec/node-protocol.md` | регистрация ноды, mTLS, формат желаемого состояния, отчёты о здоровье и трафике, повторы |
| `spec/xray-config.md` | как из сущностей получается конфиг Xray: inbound'ы, outbound'ы, правила, балансиры, DNS — с примерами входа и выхода |
| `spec/subscriptions.md` | форматы подписок, заголовки (`subscription-userinfo`, `profile-update-interval` и т. п.), определение клиента по User-Agent, примеры |
| `spec/features/*.md` | по файлу на функцию: каскады, балансир, удержание выхода, мин/макс скорость, домашняя сеть, WARP, несколько мастеров, бот и оплата, сертификаты, миграция |
| `spec/ui.md` | список страниц и сценариев (без макетов из 3x-ui, описанием словами) |
| `spec/migration.md` | как данные форка и Remnawave превращаются в сущности новой панели; что должно совпасть (UUID/пароли пользователей, токены подписок) |

Готово, когда: владелец прочитал и согласовал, по каждому файлу можно писать
код без вопросов к форку.

#### Этап B. Каркас (1 неделя)

- Репозиторий, `LICENSE`, `README`, `CLAUDE.md`/`AGENTS.md` с правилами чистой
  реализации, шаблон PR с разделом «Источники».
- CI: сборка, `go test -race`, линтер, проверка лицензий зависимостей,
  тесты с живым PostgreSQL в контейнере.
- `panel`: HTTP-сервер, конфигурация, миграции, вход администратора по паролю
  и TOTP, сессии, CSRF, ограничение попыток входа, журнал аудита.
- Пустой фронтенд с входом и каркасом страниц.

Готово, когда: `make verify` зелёный, админ входит в пустую панель, CI проверяет
лицензии.

#### Этап C. Ядро Xray на одном сервере (2–3 недели)

- Генератор конфига Xray из сущностей (`spec/xray-config.md`), тесты «сущности →
  ожидаемый JSON» на примерах из спецификации.
- Запуск и перезапуск Xray, проверка конфига перед применением (`xray -test`),
  откат на прошлый конфиг при ошибке.
- Горячее добавление/удаление пользователей через gRPC API Xray.
- Сбор счётчиков трафика, лимиты трафика и сроков, отключение пользователя.
- Протоколы первой очереди: VLESS + Reality, VLESS + XHTTP/WS + TLS, Trojan.

Готово, когда: на тестовом сервере реальный клиент подключается, трафик
считается, пользователь отключается по лимиту и сроку.

#### Этап D. Пользователи и подписки (2 недели)

- CRUD пользователей, группы, массовые операции.
- Сервер подписок: base64, JSON Xray, Clash/Mihomo, sing-box; заголовки с
  остатком трафика и сроком; определение клиента по User-Agent.
- Страница подписки для пользователя: QR, кнопки «добавить в приложение»,
  инструкции для популярных клиентов.
- Токены подписок совместимы с форком (см. `spec/migration.md`), чтобы при
  переезде ссылки не менялись.

Готово, когда: Happ, v2rayNG, v2RayTun, Streisand, sing-box и Clash Verge
импортируют подписку и подключаются.

#### Этап E. Ноды (3 недели)

- Бинарник `agent`: подключение к мастеру по mTLS, получение желаемого
  состояния, применение, отчёты о здоровье и трафике.
- Установка одной командой: одноразовый токен с мастера, скрипт ставит агент
  и systemd-юнит, нода сама регистрируется; страна по IP.
- Обновление агента с мастера, откат при неудаче.
- Работа при потере связи: нода продолжает обслуживать пользователей по
  последнему конфигу, трафик копится и отправляется после восстановления.

Готово, когда: мастер управляет 2+ нодами, выключение мастера не рвёт трафик
пользователей, после возврата мастера трафик досчитывается без дублей.

#### Этап F. Функции форка (4–6 недель)

Порядок — по важности для владельца; каждая функция — по своей спецификации
из `spec/features/`, с тестами на сценарии из таблицы 4.2.

1. Каскады «вход → выходы» и служебные связки нод (ключи генерируются сами).
2. Балансир по стране и запись «страна (авто)» в подписке.
3. Удержание выхода 15 минут и сброс при ручном выборе сервера.
4. Мин/макс скорость пользователя и уведомление в Telegram.
5. WARP одним переключателем.
6. Домашняя сеть: WireGuard, затем OpenVPN и L2TP/IPsec; правила доступа.
7. Несколько мастеров с приоритетом и возвратом главенства.
8. Сертификаты Let's Encrypt через DNS-провайдеров.

Готово, когда: все сценарии таблицы 4.2 проходят на новой панели.

#### Этап G. Остальные протоколы (по потребности, 1–3 недели)

VMess, Shadowsocks-2022, Hysteria2, TUIC, WireGuard, AmneziaWG, MTProto.
Список сокращается до того, чем владелец реально пользуется: каждый лишний
протокол — это код, тесты и поддержка.

#### Этап H. Telegram-бот и оплата (2 недели)

Уведомления пользователям (срок, трафик), продление, оплата, тарифы на
несколько месяцев, «оплачу позже» раз в 30 дней, бесплатный тариф,
уведомления админу. Платёжные провайдеры — за отдельным интерфейсом, чтобы
добавлять новые без правок ядра.

#### Этап I. Интерфейс (идёт параллельно с C–H)

Каждая серверная функция сразу получает страницу. В конце — проход по всему
UI: мобильная вёрстка, тёмная тема, русский и английский языки, понятные
ошибки.

#### Этап J. Переезд (1–2 недели)

1. Импортёр из БД форка (и из Remnawave по его REST API): пользователи с теми же
   UUID/паролями и токенами подписок, ноды, входы, тарифы, оплаты.
2. Пробный переезд копии прод-базы на тестовом стенде, сравнение подписок
   старой и новой панели для каждого пользователя (автоматический скрипт).
3. Перенос по одной ноде: на ноде ставится `agent` вместо старой панели.
4. Переключение домена подписок на новую панель; старая остаётся в режиме
   только чтения на 2 недели для отката.

Готово, когда: все пользователи на новой панели, жалоб на подключение нет
неделю, старая панель выключена.

#### Этап K. Завершение

Форк архивируется (остаётся публичным под GPL-3.0 для истории). Дальнейшая
разработка — только в новом репозитории.

## 9. Риски

| Риск | Чем грозит | Что делаем |
| --- | --- | --- |
| Своя панель затягивается | форк приходится поддерживать дольше | форк доводим до прода первым (раздел 4), новая панель не блокирует его |
| Нарушение чистой реализации (скопированный кусок кода) | новая панель становится производной от GPL | правила 8.1, раздельные роли и окружения, раздел «Источники» в PR, ревью на совпадения |
| Апстрим 3x-ui сильно меняет код | конфликты при слиянии в форк | подтягивать часто и маленькими порциями (4.4, п. 8) |
| Блокировки протоколов у провайдеров | пользователи теряют связь | несколько протоколов и транспортов, быстрая смена через шаблон с мастера |
| Потеря базы мастера | потеря пользователей и оплат | Patroni, резервные копии по расписанию с проверкой восстановления (4.4, п. 3) |

## 10. Словарь

- **Мастер** — панель, где хранятся пользователи и настройки и откуда
  управляются ноды.
- **Нода** — сервер, который обслуживает трафик пользователей и получает
  конфиг с мастера.
- **Inbound (вход)** — точка подключения клиента: протокол + порт + транспорт.
- **Outbound (выход)** — куда Xray отправляет трафик дальше: напрямую, на
  другую ноду, в WARP, в домашнюю сеть.
- **Каскад** — цепочка «входная нода → выходная нода»; пользователь подключается
  ко входу, в интернет выходит через выход.
- **Балансир** — выбор выхода из нескольких по задержке или нагрузке.
- **Удержание выхода (sticky)** — пользователь остаётся на одном выходе (и
  внешнем IP) до 15 минут после обрыва.
- **Подписка** — ссылка, по которой клиентское приложение получает список
  серверов пользователя.
- **Чистая реализация (clean room)** — написание кода с нуля по описанию
  поведения, без доступа к исходному коду, от лицензии которого уходим.
