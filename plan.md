## 1. Что это за проект

Личная VPN-панель: интерфейс и ядро [3x-ui](https://github.com/MHSanaei/3x-ui)
(Go + React, управляет Xray-core) плюс модель «мастер + ноды» в духе
Remnawave. Один мастер хранит пользователей и настройки, ноды (другие
инстансы панели) только обслуживают трафик и получают конфиг с мастера.

Цели владельца:

- все протоколы Xray (VLESS/Reality, VMess, Trojan, SS-2022, Hysteria2, TUIC,
  WireGuard, AmneziaWG, MTProto) из одной панели;
- ноды добавляются одной командой, настраиваются только с мастера;
- каскады «вход → выход» в два клика, балансировка по скорости внутри страны,
  удержание выхода (IP) 15 минут;
- минимальная и максимальная скорость на пользователя;
- доступ пользователей к домашней сети по правилам «кто → какая подсеть/IP»;
- WARP одним переключателем;
- 2–3 мастера с автоматическим переключением и возвратом главенства;
- оплата и продление через Telegram-бота, удобная страница подписки;
- в будущем — собственная панель, не зависящая от кода 3x-ui (раздел 8).

Проект личный, используется владельцем, репозиторий публичный.

## 2. Стек и устройство

| Часть | Технологии |
| --- | --- |
| Бэкенд | Go 1.27, Gin, GORM; модуль `github.com/mhsanaei/3x-ui/v3` (оставлен, чтобы чисто подтягивать апстрим) |
| БД | PostgreSQL (основная для форка, `XUI_DB_TYPE=postgres`, `XUI_DB_DSN=...`), SQLite по умолчанию у апстрима |
| Прокси-ядро | Xray-core как дочерний процесс + его Go-пакеты для конфигов и gRPC API |
| Доп. процессы | `mtg-multi` (MTProto), встроенные TUIC и AmneziaWG на Go |
| Фронтенд | React 19 + Ant Design 6 + Vite 8 + TypeScript, собирается в `internal/web/dist/` и встраивается в бинарник |
| Документация | `docs/` — отдельный сайт Next.js/Fumadocs (pnpm) |

Ключевые идеи (подробно в `docs/architecture.md`):

- **БД → конфиг Xray.** Inbound'ы и клиенты лежат в БД, при изменении конфиг
  пересобирается и применяется «горячо» через gRPC API Xray, перезапуск — только
  когда иначе нельзя.
- **`runtime.Runtime`.** Любая операция, меняющая inbound/клиента, идёт через
  интерфейс `Local` (своя Xray) или `Remote` (нода по HTTPS/mTLS). Прямой вызов
  `internal/xray/api.go` из контроллера или cron-задачи ломает мультинодовую
  схему, хотя все локальные тесты проходят.
- **Сервер подписок** (`internal/sub/`) — отдельный HTTP-сервер для клиентов
  (raw / JSON / Clash).

Где что лежит (новое в форке отмечено ★):

| Путь | Назначение |
| --- | --- |
| `main.go` | точка входа и CLI `x-ui` (в т. ч. ★ `x-ui cluster ...`) |
| `internal/database/` | модели GORM, миграции в `db.go` |
| `internal/xray/` | процесс Xray, генерация конфига, gRPC API |
| `internal/web/controller/` | REST API панели |
| `internal/web/service/` | бизнес-логика; ★ `cascade*.go`, `sub_balancer.go`, `speed.go`, `home_network.go`, `warp_switch.go`, `master_cluster.go`, `managed_template.go`, `node_join.go` |
| `internal/web/job/` | cron-задачи (трафик, синк нод, лимиты и т. д.) |
| `internal/web/runtime/` | Local/Remote, связь мастер–нода по mTLS |
| ★ `internal/nodejoin/` | установка ноды одной командой (`install-node.sh`, бандл) |
| ★ `internal/homenet/` | туннели домашней сети (WireGuard / OpenVPN / L2TP) |
| ★ `internal/shaper/` | ограничение скорости через `tc` |
| `internal/sub/` | подписки |
| `frontend/src/pages/nodes/` | ★ страницы «Ноды», «Каскады», «Домашние сети», «WARP», «Мастеры», «Ограничения скорости» |
| `tools/openapigen/` | генерация типов и OpenAPI из Go-структур |

★-пути появляются в `main` после слияния PR #1 (см. раздел 3).

## 4. Дорожная карта форка (ближайшее)

Делать по порядку, каждый пункт — отдельный PR в `main`:

1. **Слить открытые PR** в порядке из раздела 3, починить конфликты.
2. **Проверка на стенде**: пункты «проверено только тестами» из раздела 3,
   найденные ошибки — отдельными `fix(...)` PR с тестом-воспроизведением.
3. **Hysteria из Remnawave** в миграции (PR #14) — когда будет образец ссылки.
4. **Наблюдаемость нод**: история скорости и задержки выходов каскада на
   странице «Ноды», чтобы видеть, почему балансир выбрал выход.
5. **Резервные копии мастера**: регулярный `pg_dump` по расписанию с отправкой
   в Telegram или S3-совместимое хранилище.
6. **Обновление нод с мастера** одной кнопкой (сейчас — командой на каждой ноде).
7. **Подтягивание апстрима 3x-ui** раз в 1–2 недели: `git merge upstream/main`,
   `make verify`, PR `chore(upstream): merge 3x-ui <дата>`.

Параллельно (не блокирует форк) — подготовка своей панели, раздел 8.

## 5. Сборка, запуск, проверки

Требования: Go 1.27+ (`GOTOOLCHAIN=auto` скачает нужную), Node.js 26 и npm 11
(`.nvmrc`), C-компилятор (SQLite-драйвер на CGo), для docs — pnpm.

```bash
make dist-stub                 # один раз в свежем клоне, иначе go build падает
cd frontend && npm ci && npm run build && cd ..
go build -o x-ui .
XUI_DEBUG=true go run .        # панель на :2053; после npm run build перезапускать
```

PostgreSQL для разработки:

```bash
docker run -d --name xui-pg -e POSTGRES_PASSWORD=xui -e POSTGRES_USER=xui -e POSTGRES_DB=xui -p 5432:5432 postgres:17
export XUI_DB_TYPE=postgres XUI_DB_DSN='postgres://xui:xui@127.0.0.1:5432/xui?sslmode=disable'
```

Проверки:

| Команда | Что делает |
| --- | --- |
| `make verify` | основной локальный гейт: генерация, линтеры, типы, тесты Go и фронтенда, сборка, storybook, свежесть OpenAPI |
| `make test-go` | только Go-тесты (быстрее `go test ./...`, сам делает `dist-stub`) |
| `cd frontend && npm test` | тесты фронтенда (включая проверку мёртвых i18n-ключей) |
| `make race` | Go-тесты с `-race` — обязательно при правке синхронизации, нод, трафика |
| `make node-e2e` | живые мастер + нода (`XUI_NODE_E2E_BINARY`) |
| `XUI_TEST_PG_DSN=... make test-go` | Postgres-тесты (без переменной они пропускаются) |
| `make gen` | перегенерировать типы/OpenAPI после правки Go-структур API |

Линтер Go должен быть собран тем же Go 1.27:
`GOTOOLCHAIN=go1.27.3 go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.15.0`.

CI — GitHub Actions на раннерах GitHub (`.github/workflows/ci.yml`,
`docs-ci.yml`). Self-hosted раннеры для этого публичного репозитория не
использовать: чужой PR смог бы выполнить код на машине владельца.

### Тестовый стенд

У владельца есть стенд на Proxmox: контейнер с тестовой панелью-мастером,
контейнер с тестовой нодой и отдельная продовая нода, которую трогать нельзя.
Адреса и доступы в репозиторий не пишутся — спросите владельца. Правила:

- работать только в выделенных тестовых контейнерах, другие ВМ/CT не трогать;
- любые действия на живых серверах (не тестовых) — только с явного разрешения;
- никаких секретов, токенов, паролей, ключей и внутренних адресов в коммитах,
  PR, issue и комментариях — репозиторий публичный.

## 6. Правила работы

Полный список — в `CLAUDE.md`. Самое важное:

- **Ветки и PR.** Одна задача — одна ветка — один PR в `main`. Прямые пуши в
  `main` запрещены. Назначать `NeciMNK` исполнителем PR (ревьюером назначить
  нельзя, если PR создан от его имени).
- **Коммиты** — conventional: `type(area): короткое повелительное описание`,
  в теле — зачем. Типы: `fix`, `feat`, `chore`, `refactor`, `perf`, `docs`,
  `style`. Рефакторинг отдельно от фич.
- **TDD.** Баг → сначала тест, который падает по описанной причине, потом
  исправление. Фейковые тесты (геттеры, пересчёт той же формулой, слабые
  проверки вроде `err != nil`, перегенерированные снимки) запрещены.
- **Правильное исправление, а не маленькое.** Ищите корень проблемы; заплатки,
  скрывающие симптом, не принимаются.
- **Слои.** Изменение inbound/клиента — только через `runtime.Runtime`.
  Изменение модели БД — только с миграцией в `internal/database/db.go`.
- **API.** Новый маршрут в `internal/web/controller/` → запись в
  `frontend/src/pages/api-docs/endpoints.ts` → `make gen` → копия
  `frontend/public/openapi.json` в `docs/public/` → `cd docs && pnpm gen:api`.
- **i18n.** Новый ключ — во все 14 файлов `internal/web/translation/` и сразу
  используется в коде. Интерфейс форка — русский и английский, остальные
  локали можно заполнять английским текстом.
- **Комментарии в коде** — не длиннее 2 строк, объясняют «почему», а не «что».
- **Язык.** Код, коммиты и комментарии — по-английски; документы для владельца
  (`plan.md`, `FORK.ru.md`) и описания PR — по-русски.

### Как работать ИИ-агенту

1. Прочитать `plan.md`, `CLAUDE.md`, нужный раздел `docs/architecture.md`.
2. Взять задачу из раздела 4 (или из issue), создать ветку `<agent>/<кратко>`.
3. Писать тест → код → `make verify` (и `make race`/Postgres/node-e2e, если
   задеты БД, ноды или синхронизация).
4. Открыть PR по шаблону `.github/pull_request_template.md`, по-русски
   описать что и зачем, указать, что проверено, а что нет.
5. Обновить таблицы состояния в разделе 3 этого файла в том же PR.
6. Не делать необратимых действий (прод-серверы, удаление данных, публикация
   секретов) без явного разрешения владельца.

## 7. Лицензия: что можно и чего нельзя

Код 3x-ui распространяется по **GPL-3.0**. Всё, что сделано в этом
репозитории поверх него (включая новые файлы форка, которые вызывают код
3x-ui и собираются с ним в один бинарник), — производная работа и тоже
распространяется только по GPL-3.0. Сменить лицензию этого репозитория
нельзя: на код апстрима у нас нет прав, а его авторов сотни.

Что GPL-3.0 реально требует:

- при передаче бинарника кому-либо — дать и исходники под той же лицензией;
- сохранять `LICENSE`, указания авторства и отметку об изменениях (`NOTICE.md`).

Чего GPL-3.0 **не** требует: публиковать код, если панель используется только
самим владельцем или как сетевой сервис (это не AGPL); не запрещает платные
подписки для пользователей VPN. Для личного проекта лицензия почти ничем не
мешает. Уходить от неё имеет смысл, только если нужна закрытая или другая
лицензия (продажа панели, закрытый код).

Почему нельзя «просто переписать файлы» здесь же: переименование, перенос в
другой репозиторий, переформатирование или переписывание функций по одной,
глядя на оригинал, оставляют работу производной. Уйти от GPL можно только
**чистой реализацией (clean room)**: новый код пишется с нуля по спецификации
поведения, без копирования и без построчного пересказа кода 3x-ui. Идеи,
протоколы, форматы ссылок и подписок, API Xray авторским правом не защищены —
их можно повторять.

Код Remnawave (AGPL-3.0) и других панелей (Marzban, Marzneshin, Hiddify и т. п.)
не копировать ни в форк, ни в новую панель — только идеи.

Это не юридическая консультация. Перед выпуском своей панели под другой
лицензией стоит показать этот раздел и историю разработки юристу.

## 8. Путь к собственной независимой панели

Цель: отдельный проект с собственной лицензией (выбирает владелец: MIT/Apache-2.0
или закрытая), в котором нет кода 3x-ui. Форк продолжает работать, пока новая
панель не догонит его по функциям, затем пользователи переносятся миграцией.

Масштаб: в форке около 110 тыс. строк Go (без тестов) и около 120 тыс. строк
TypeScript. Переписывать один в один не нужно — новая панель делается под
наши сценарии (мастер + ноды, PostgreSQL), без наследия SQLite, Windows и
редких функций апстрима.

### Правила чистой реализации

1. **Отдельный репозиторий** (например, `NeciMNK/<новое имя>`), новый Go-модуль,
   своя структура пакетов, своя схема БД, свой `LICENSE` с первого коммита.
2. **Две роли.** «Аналитик» может читать код форка и пишет спецификации
   поведения в `spec/` нового репо: что делает функция, входы/выходы, форматы,
   граничные случаи — словами и примерами, без кода и без имён внутренних
   функций 3x-ui. «Разработчик» пишет код только по спецификации, документации
   Xray и открытым стандартам и **не открывает** исходники 3x-ui и форка.
3. **Для ИИ-агентов**: агент-разработчик запускается в окружении, где есть
   только новый репозиторий (без клона форка), в промпт не вставляются куски
   кода 3x-ui. Спецификации пишет отдельная сессия.
4. **Журнал происхождения.** В каждом PR нового репо указывать, по каким
   спецификациям и внешним документам написан код. Это доказательство
   независимости, если вопрос когда-нибудь возникнет.
5. **Сторонние зависимости** проверять по лицензии: Xray-core (MPL-2.0) как
   библиотека и как отдельный бинарник допустим при любой лицензии своего кода
   (изменённые файлы самого Xray остаются под MPL); MIT/Apache/BSD — свободно;
   GPL/AGPL-зависимости в новый бинарник не тянуть. Геобазы (GPL-3.0) скачивать
   как отдельные файлы данных, не встраивать.
6. **Код, написанный в форке нами**, тоже не переносить копированием: он
   вырос внутри кода 3x-ui и вызывает его. Его поведение описывается в
   спецификации и реализуется заново, как и всё остальное.

### Этапы

| Этап | Результат | Готово, когда |
| --- | --- | --- |
| A. Спецификации | `spec/`: модель данных (пользователи, тарифы, inbound'ы, ноды, каскады, домашние сети), REST API, протокол мастер–нода, форматы подписок, сценарии UI | по спецификации можно писать без вопросов к коду форка |
| B. Каркас | новый репо, лицензия, CI, Go-сервис, PostgreSQL + миграции, авторизация админа (пароль + 2FA), журнал аудита | `make verify` зелёный, админ входит в пустую панель |
| C. Ядро Xray | генератор конфига Xray из БД, запуск/перезапуск процесса, горячее применение через gRPC API, сбор трафика | один сервер раздаёт VLESS/Reality и Trojan с учётом трафика |
| D. Пользователи и подписки | клиенты, лимиты трафика и сроков, сервер подписок (raw, JSON, Clash, sing-box), страница подписки | клиент из Happ/v2rayNG подключается по ссылке из подписки |
| E. Ноды | агент ноды (отдельный лёгкий бинарник), установка одной командой, mTLS, синхронизация конфигов и трафика с мастера | мастер управляет 2+ нодами, падение ноды не ломает мастер |
| F. Функции форка | каскады, балансир по стране, удержание выхода, мин/макс скорость, домашняя сеть, WARP, несколько мастеров | каждая функция проходит те же сценарии, что в форке |
| G. Остальные протоколы | VMess, SS-2022, Hysteria2, TUIC, WireGuard/AmneziaWG, MTProto — по реальной потребности | используемые владельцем протоколы работают |
| H. Бот и оплата | Telegram-бот: уведомления, продление, оплата, тарифы | сценарии бота из форка повторены |
| I. Интерфейс | новый фронтенд (свой дизайн и компоненты, допустимы MIT-библиотеки вроде Ant Design) | все операции доступны из UI |
| J. Переезд | импортёр из БД форка (чтение чужого формата данных — совместимость, а не копирование), прогон на стенде, перенос нод по одной | все пользователи на новой панели, ссылки подписок не поменялись |
| K. Завершение | форк архивируется или остаётся как GPL-проект только для истории | — |

Этапы B–E можно начинать параллельно форку; F–J — после того как форк
стабилен на проде. Каждый этап — серия небольших PR в новом репозитории со
своими тестами.

### Что решить владельцу перед стартом

- лицензия новой панели (открытая MIT/Apache-2.0 или закрытая);
- название и новый репозиторий;
- какие протоколы реально нужны (чем меньше, тем быстрее этап G);
- кто будет «аналитиком» (может быть ИИ-сессия с доступом к форку) и кто
  «разработчиком» (сессия без доступа к форку).
