# План перехода с Remnawave на my-panel-vpn

[English version](migration-plan.en.md) · [Общий план работ](plan.md) ·
[Справка по окну переноса](docs/content/docs/ru/operations/migrate-from-other-panels.mdx)

Цель: перевести пользователей, ноды, подписки и бота с Remnawave на эту панель
так, чтобы пользователи ничего не заметили: те же ссылки подписок, те же
конфиги в приложениях, никаких «обновите подписку». Перерыв в работе VPN —
1–3 минуты в одном заранее выбранном ночном окне.

Коротко:

| | Время |
| --- | --- |
| Подготовка (можно растянуть на несколько дней, VPN работает как обычно) | 4–7 часов работы |
| Переключение (окно, когда VPN недоступен) | 1–3 минуты простоя, 30–60 минут работы в окне |
| Наблюдение, возможен откат одной командой | 1–3 суток |
| Удаление Remnawave | через 7 дней, 30 минут |

Итого: **1 рабочий день активной работы + неделя страховки**. Быстрее всего —
подготовка днём, переключение в тот же вечер, наблюдение до конца недели.

---

## 0. Как устроен переход и почему он незаметен

Пользователь хранит в приложении две вещи: ссылку подписки и конфиги,
полученные по ней. Перенос сохраняет обе:

- **Конфиги.** UUID VLESS, пароли Trojan/Shadowsocks, аутентификация Hysteria2
  (`vlessUuid`), порты, ключи и `shortIds` Reality, SNI и адреса хостов
  переносятся как есть. Ноды этой панели ставятся **на те же серверы** и
  занимают **те же порты**, поэтому старый конфиг в приложении просто
  подключается к новому Xray.
- **Подписка.** ID подписки (`shortUuid`) становится `subId` клиента, а путь и
  адрес подписок берутся из `subscriptionUrl` Remnawave. После переключения
  домена подписок на эту панель старая ссылка отдаёт тот же набор конфигов
  (на копии живого Remnawave совпали 15 из 15 подписок, PR #34).
- **Остальное.** Лимит и израсходованный трафик, срок, стратегия сброса,
  Telegram ID, описание, лимит устройств (HWID), отключённые пользователи,
  названия конфигов (шаблон `{{HOST}}`), фильтры хостов по internal squads.

Remnawave при переносе **только читается** — поэтому откат всегда возможен,
пока в новой панели не накопились изменения (раздел 6).

Почему переключение делается разом, а не по одной ноде: импорт пропускает
клиентов, которые уже есть (по email). Если перенести сначала одну ноду, а
потом вторую, клиенты второй ноды к ней уже не привяжутся. Поэтому все
`remnanode` останавливаются вместе и импорт запускается **один раз**.

## 1. Что не переносится и что сделать с этим заранее

| Что | Что делать | Когда |
| --- | --- | --- |
| Маршрутизация, outbounds и DNS из config profile Remnawave (блок торрентов, WARP, geosite-правила) | перенести вручную в шаблон Xray мастера и нод (**Настройки Xray** с выбором ноды вверху); WARP — переключателем «Ноды → WARP» | шаг 2.4 |
| TLS-сертификаты, которые remnanode читает с диска (Hysteria, VLESS/Trojan по TLS), например `/opt/certs/...` | скопировать по тому же пути на сервер ноды; окно переноса перечислит все такие файлы | шаг 2.5 |
| External squads, xhttp extra params хостов | проверить, используются ли; если да — повторить руками после импорта | шаг 2.6 |
| Списки устройств HWID | ничего: лимит сохраняется, устройства регистрируются заново при следующем обновлении подписки | — |
| Пользователь с Trojan и Shadowsocks под разными паролями | его конфиг Shadowsocks заработает только после обновления подписки; окно переноса покажет таких поимённо — напишите им заранее или смиритесь с одним обновлением | шаг 2.6 |
| Заголовок подписки, ссылка поддержки, объявление, интервал обновления, профиль маршрутизации Happ | выставить в **Настройки → Подписка** так же, как в Remnawave, иначе после обновления подписки в приложении поменяется название профиля | шаг 2.7 |
| Внешний бот-магазин и платёжки, работающие через API Remnawave | перестанут работать; их заменяет бот этой панели (раздел 2.8) | шаг 2.8 |
| История платежей и балансы во внешнем боте | не переносятся: оплаченный срок уже лежит в `expiryTime`, историю сохраните выгрузкой из старого бота | шаг 2.8 |

## 2. Подготовка (VPN работает, пользователи ничего не видят)

### 2.1. Инвентаризация Remnawave — 20–30 минут

Записать в заметку (не в репозиторий — он публичный):

- адрес панели Remnawave, домен и путь подписок (пример ссылки пользователя);
- список нод: имя, адрес, какие inbound'ы и порты на каждой;
- что есть в config profile кроме inbound'ов: routing, outbounds, DNS;
- откуда берутся TLS-сертификаты на нодах (пути к файлам);
- кто ещё ходит в API Remnawave: бот-магазин, скрипты, мониторинг;
- токен Telegram-бота и что он делает (уведомления, продажи);
- настройки подписки: заголовок, support URL, announce, интервал обновления.

Создать в Remnawave API-токен (**Settings → API Tokens**) — только для чтения
данных при импорте.

### 2.2. Резервные копии — 15 минут

На сервере Remnawave:

```bash
cd /opt/remnawave
docker compose exec -T remnawave-db pg_dumpall -U postgres > ~/remnawave-$(date +%F).sql
cp .env docker-compose.yml ~/   # и конфиг Caddy/nginx, если он отдельно
```

Скопировать файлы с сервера к себе. Это страховка на случай, если откат
понадобится через неделю и что-то пойдёт не так.

### 2.3. Мастер этой панели — 30–60 минут

Поставить мастер (`install.sh`, PostgreSQL) — на отдельный сервер или на
сервер Remnawave. Если на тот же сервер: порты панели (`2053`) и подписок
(`2096`) не пересекаются с Remnawave (`3000`, `3010`), домен подписок
переключим позже на шаге 3.4.

Сразу:

- сменить логин/пароль и путь панели, включить двухфакторную аутентификацию;
- выпустить сертификат для домена подписок (**Сертификаты**, Cloudflare DNS);
  после выпуска он сам подставится в настройки подписки (PR #32);
- включить резервную копию в Telegram (**Настройки → Telegram**).

### 2.4. Шаблон Xray: маршрутизация и outbounds — 30–90 минут

Перенести из config profile Remnawave всё, что не inbound'ы: правила
`routing`, `outbounds` (WARP, блок-лист, прямой выход), `dns`. Где есть
готовая функция панели — использовать её (WARP одним переключателем, прокси
панели). Остальное — **Настройки Xray** → выбрать ноду (или мастер) → правила, outbounds, DNS. Шаблон хранится на мастере и сам уходит на ноды.

### 2.5. Ноды на серверах Remnawave — 10 минут на ноду (5 нод ≈ 45 минут)

На каждом сервере, где работает `remnanode`:

1. **Ноды → Добавить** на мастере, выполнить выданную команду на сервере.
   Порт панели ноды выбирается свободный, `remnanode` и его `NODE_PORT` не
   задеваются. Новая нода пока без подключений — порты Xray свободны у
   `remnanode`.
2. Проверить, что нода онлайн на мастере.
3. Если в профиле есть TLS-inbound'ы — скопировать сертификаты по тем же
   путям (`/opt/certs/...`) и убедиться, что их читает пользователь, от
   которого работает нода.
4. Проверить, что фаервол пропускает порт панели ноды с мастера.

### 2.6. Пробный прогон на стенде — 1–2 часа (обязательно)

Сделать снимок Remnawave (скрипт в
[справке](docs/content/docs/ru/operations/migrate-from-other-panels.mdx), раздел «Файл-снимок Remnawave»)
и импортировать его в **тестовый** мастер. Проверить:

- **Проверить** в окне переноса: каждая нода Remnawave сопоставлена с нодой
  этой панели, нет конфликтов портов, список «Замечания» прочитан целиком;
- 5–10 подписок разных пользователей (обычный, с ограниченными сквадами,
  отключённый, истёкший, с Hysteria): содержимое совпадает с ответом
  Remnawave по той же ссылке — сравнить `curl` обеих подписок и `diff`
  декодированного base64;
- с тестовым пользователем — реальное подключение в Happ/v2rayN к тестовой
  ноде старым конфигом.

Тестовый мастер после прогона откатить к пустой базе.

### 2.7. Настройки подписки — 15 минут

На боевом мастере в **Настройки → Подписка** выставить то же, что было в
Remnawave: заголовок подписки, ссылку поддержки, объявление, интервал
обновления, профиль маршрутизации для Happ (если был). Галочку «Взять пути и
адрес подписок старой панели» в окне переноса не снимать — она сама выставит
путь и `subURI`.

### 2.8. Бот и оплата — 30–60 минут

Бот этой панели показывает клиенту срок, сумму и реквизиты, принимает оплату
на несколько месяцев, «оплачу позже» и бесплатный тариф; оплату
подтверждает админ одной кнопкой. Онлайн-эквайринга (ЮKassa, CryptoBot и т. п.)
нет — если во внешнем боте он был, это осознанное изменение для клиентов.

- **Telegram ID переносятся**, поэтому бот узнаёт клиентов сразу после импорта.
- Можно оставить того же бота (клиентам ничего не искать): в момент
  переключения остановить старый бот и вписать **тот же токен** в
  **Настройки → Telegram**. Один токен может читать только один процесс; если
  старый бот работал через webhook, снять его:
  `curl "https://api.telegram.org/bot<TOKEN>/deleteWebhook"` — бот панели
  работает через long polling.
- Заранее заполнить цены, скидки, реквизиты и бесплатный тариф
  (**Финансы**, **Настройки → Telegram → Оплата**).
- Выгрузить историю платежей и балансы из старого бота (если они есть) —
  сюда они не импортируются. Пользователям с положительным балансом заранее
  продлить срок в Remnawave на эту сумму, тогда срок перенесётся сам.
- Скрипты и сервисы, ходившие в API Remnawave, перевести на API этой панели
  (`/panel/api/...`, токен в **Настройки → Безопасность → API-токены**; оплата —
  `/panel/api/billing/client` и `/pay`).

### 2.9. DNS заранее — 2 минуты (за сутки до окна)

Если домен подписок будет переключаться через DNS (мастер на другом сервере),
понизить TTL записи до 60 секунд **за 24 часа** до окна, иначе часть
приложений ещё сутки будет ходить на старый сервер.

## 3. Переключение (окно 30–60 минут, простой VPN 1–3 минуты)

Выбрать время с минимальной нагрузкой (ночь). Открыть заранее: мастер на
окне переноса, SSH-сессии ко всем нодам, Remnawave в соседней вкладке.

### 3.1. Последняя проверка — 5 минут

Окно переноса (**Настройки → Перенести из…**) → адрес Remnawave и API-токен → **Проверить**. Ноды
сопоставлены, конфликтов портов нет, замечания знакомы по пробному прогону.

### 3.2. Остановить remnanode на всех нодах — 1 минута

Одновременно на всех серверах (например, заранее набранной командой в
каждой SSH-сессии):

```bash
cd /opt/remnanode && docker compose down
```

С этого момента VPN недоступен. Remnawave (панель) **не останавливать** —
импорт читает данные из неё.

### 3.3. Перенести — 1–2 минуты

Сразу нажать **Перенести** (галочка путей подписок включена). Подключения
создаются на нодах, Xray занимает те же порты с теми же ключами; панель
перезапустит сервер подписок. После этого VPN снова работает.

Проверить итог: «Перенесено: подключений N, клиентов M, хостов K» совпадает с
пробным прогоном, список «Не перенесено» пуст или ожидаем. Повторный
**Перенести** ничего не дублирует, если что-то нужно дотащить.

### 3.4. Переключить домен подписок — 5–15 минут

- Мастер на сервере Remnawave: в Caddy/nginx заменить `reverse_proxy`/
  `proxy_pass` домена подписок с `subscription-page`/Remnawave на
  `127.0.0.1:2096` и перезагрузить прокси.
- Мастер на другом сервере: сменить A-запись домена подписок на адрес
  мастера (TTL уже 60 с) или запустить сервер подписок прямо на `443` с
  сертификатом домена.

Затем остановить контейнеры Remnawave и `subscription-page`, чтобы никто
случайно не изменил там данные:

```bash
cd /opt/remnawave && docker compose stop
```

### 3.5. Бот — 5 минут

Остановить старый бот, при необходимости `deleteWebhook`, вписать токен в
**Настройки → Telegram**, написать боту `/start` со своего аккаунта и с
тестового клиента.

### 3.6. Проверка после переключения — 15–30 минут

- Ссылки 3–5 реальных пользователей открываются и отдают то же, что в
  пробном прогоне (`curl` + `diff`).
- Подключение своим приложением **без обновления подписки** на каждую ноду.
- **Ноды**: все онлайн, у подключений растёт трафик.
- Страница подписки в браузере открывается по старой ссылке.
- Бот отвечает, тестовая оплата проходит до подтверждения админом.

Если любой пункт не проходит и быстро не чинится — откат (раздел 5).

## 4. Наблюдение — 1–3 суток

- Трафик клиентов считается, сроки и лимиты срабатывают (у кого истёк срок —
  отключён).
- Нет жалоб «не подключается» в боте/поддержке. Пользователи, у которых
  поменялся конфиг Shadowsocks (раздел 1), — получили его после обновления
  подписки.
- Устройства HWID регистрируются заново, никто не упирается в лимит.
- В логах мастера и нод нет повторяющихся ошибок.
- Резервная копия мастера пришла в Telegram и восстанавливается на тестовом
  мастере.

## 5. Откат

Remnawave не менялся, поэтому откат — обратное переключение. Время: 5–10
минут, простой VPN — около минуты.

1. На всех нодах остановить ноду этой панели и вернуть `remnanode`:

   ```bash
   systemctl stop x-ui && systemctl disable x-ui
   cd /opt/remnanode && docker compose up -d
   ```

2. `cd /opt/remnawave && docker compose up -d`.
3. Вернуть прокси/DNS домена подписок на Remnawave.
4. Остановить бота этой панели (очистить токен в **Настройки → Telegram**) и
   запустить старый бот.
5. Всё, что изменилось в новой панели после переключения (новые
   пользователи, оплаты, продления), внести в Remnawave руками: возьмите
   список из **Финансы** и журнала бота.

Точка невозврата: чем дольше работает новая панель, тем больше ручной работы
в п. 5. Решение «остаёмся» принять в течение 3 суток.

## 6. Завершение — через 7 дней, 30 минут

- Удалить `remnanode` с нод: `cd /opt/remnanode && docker compose down -v`,
  удалить каталог.
- Удалить Remnawave (`docker compose down -v` в `/opt/remnawave`), оставив
  дамп базы из шага 2.2 в архиве ещё на месяц.
- Отозвать API-токен Remnawave, вернуть обычный TTL DNS.
- Отметить переезд в [`plan.md`](plan.md), раздел 3.
