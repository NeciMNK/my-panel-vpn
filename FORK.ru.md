# my-panel-vpn — личная панель на базе 3x-ui с нодами в стиле Remnawave

Эта ветка начинается с полной истории [3x-ui](https://github.com/MHSanaei/3x-ui)
(GPL-3.0, файл `LICENSE` сохранён), поэтому обновления оттуда подтягиваются
обычным `git merge`:

```bash
git remote add upstream https://github.com/MHSanaei/3x-ui.git
git fetch upstream main
git merge upstream/main
```

Код Remnawave (TypeScript, AGPL-3.0) напрямую не вливается: он на другом языке
и с другой схемой данных. Из него берутся идеи: управление конфигом нод с одного
мастера, добавление ноды одной командой, профили конфигурации и «сквады».

## Что уже есть в 3x-ui v3 (бесплатно получаем)

| Требование | Состояние в 3x-ui |
| --- | --- |
| Все протоколы и транспорты Xray (VLESS/Reality, VMess, Trojan, SS-2022, WireGuard, Hysteria2, TUIC, AmneziaWG, MTProto, HTTP/SOCKS, Tunnel) | есть |
| Мастер управляет нодами (другие инстансы 3x-ui) по HTTPS/mTLS, синхронизация inbound'ов, клиентов, трафика | есть |
| PostgreSQL вместо SQLite (`XUI_DB_TYPE=postgres`, `XUI_DB_DSN=...`) | есть |
| WARP (регистрация, outbound) | есть, но настраивается на каждой ноде отдельно |
| Балансировщики Xray (leastPing / leastLoad), observatory | есть, но вручную и на каждой ноде |
| Группы клиентов, хосты для подписок | есть |

Главное, чего не хватает: мастер синхронизирует только inbound'ы и клиентов,
а outbound'ы, маршрутизация, WARP и балансировщики живут в локальном шаблоне
Xray каждой ноды. Поэтому этап 1 — фундамент для всего остального.

## План по этапам

### Этап 0. База (эта ветка)
Импорт 3x-ui с историей, проверка сборки (Go 1.27 + фронтенд на Node 26), этот документ.

### Этап 1. Профили конфигурации Xray с мастера на ноды
- На мастере появляется сущность «Профиль ноды»: outbound'ы, правила маршрутизации,
  балансировщики, DNS. Профиль назначается ноде, мастер сам вычисляет итоговый
  конфиг ноды и отправляет его через существующий `runtime.Remote`.
- Применение без разрыва соединений там, где Xray это позволяет
  (gRPC API для outbound'ов и правил), перезапуск Xray только когда без него никак.
- Всё дальнейшее (каскады, WARP, домашняя сеть, балансировщик) — генераторы,
  которые дописывают куски в профиль.

### Этап 2. Добавление ноды одной командой
- Кнопка «Добавить ноду» на мастере выдаёт команду вида
  `bash <(curl -Ls https://мастер/install-node.sh) --join <одноразовый токен>`.
- Скрипт ставит 3x-ui в режиме ноды, сам выпускает mTLS-сертификат,
  регистрируется на мастере и появляется в списке нод. Ручной ввод адреса,
  порта и токена не нужен.
- Поле «страна» у ноды определяется по IP автоматически (можно поправить).

### Этап 3. Каскады в 2 клика
- Мастер: «Каскад» → выбрать входную ноду → выбрать выходную(ые) ноду(ы).
- Мастер создаёт на выходной ноде служебный inbound VLESS+Reality для связки
  нод (ключи генерируются сами), на входной — outbound к нему и правило
  маршрутизации. Пользователи об этом не знают, в подписке остаётся вход.
- «Добавить сервер в каскад» = добавить ещё одну выходную ноду, при двух и более
  выходах автоматически включается балансировщик.
- Цепочки длиннее двух нод (вход → транзит → выход) делаются тем же механизмом.

### Этап 4. Балансировщик по скорости на страну
- Ноды группируются по стране. Для каждой страны создаётся балансировщик Xray
  `leastLoad` с `burstObservatory` (замер задержки/доступности каждые N секунд)
  по всем нодам страны.
- В подписке у пользователя появляется запись «🇩🇪 Германия (авто)» плюс
  отдельные серверы для ручного выбора. Новая нода страны попадает в балансир сама.

### Этап 5. Липкие сессии (15 минут, сохранение IP)
- Пользователь, вошедший через «страну (авто)», закрепляется за конкретной
  выходной нодой. Балансировщик не перекидывает его на другую, пока он онлайн.
- При обрыве не по воле пользователя закрепление держится 15 минут: переподключение
  попадает на ту же выходную ноду, внешний IP не меняется.
- Если пользователь сам выбрал в клиенте другой сервер (подключился к конкретной
  записи из подписки), ограничение не действует, закрепление сбрасывается.
- Реализация: онлайн-статистика Xray по пользователям + правила маршрутизации
  по `user`, которые мастер добавляет/снимает через gRPC API без перезапуска Xray.

### Этап 6. Домашняя сеть
- Сущность «Домашняя сеть»: тип подключения (WireGuard, OpenVPN или L2TP/IPsec),
  параметры, подсети дома (например `192.168.1.0/24`), какая нода держит туннель.
- WireGuard — нативный outbound Xray. OpenVPN и L2TP — системный клиент на ноде
  (ставится и управляется панелью), Xray привязывается к его интерфейсу.
- Подсети и адреса задаются вручную: у каждой домашней сети свой список
  подсетей (`192.168.1.0/24`) и отдельных IP (`192.168.1.10`).
- Правила доступа «кто → куда»: пользователю или группе выдаётся доступ к
  конкретной домашней сети целиком, к части её подсетей или только к отдельным IP.
  Добавить пользователя в такое правило — одна кнопка в карточке клиента.
- Трафик в разрешённые адреса идёт в туннель (с любой ноды, через связку нод из
  этапа 3), всё остальное в домашние подсети закрыто.

### Этап 7. WARP одним переключателем
- Тумблер WARP у ноды или у профиля: «весь трафик» / «только выбранные сайты».
  Регистрация WARP и outbound уже есть в 3x-ui, остаётся вынести это на мастер.

### Этап 8. Несколько мастеров с автоматическим переключением
- 2–3 мастера с приоритетами. PostgreSQL в кластере с потоковой репликацией
  и автоматическим failover (Patroni). Для кворума нужно минимум 3 узла
  (третьим может быть лёгкий «свидетель» на любой ноде).
- Панель работает на каждом мастере, но фоновые задачи (синк нод, учёт трафика)
  выполняет только лидер. Лидер выбирается по приоритету; когда главный мастер
  возвращается, он забирает лидерство обратно.
- Ноды доверяют всем мастерам (общий mTLS CA), адрес панели и подписок
  переключается на лидера (DNS с коротким TTL или плавающий IP).

## Несколько мастеров: как развернуть

Схема на три машины: `m1` (главный мастер), `m2` (запасной мастер) и `w`
(«свидетель», любая нода или маленький VPS). Кворуму etcd нужно три голоса,
поэтому свидетель обязателен, иначе при падении одного мастера второй не
узнает, можно ли ему становиться главным.

### 1. etcd на всех трёх машинах

```bash
apt install -y etcd-server etcd-client
```

`/etc/default/etcd` на `m1` (на `m2` и `w` меняются имя и адрес):

```bash
ETCD_NAME=m1
ETCD_DATA_DIR=/var/lib/etcd
ETCD_LISTEN_PEER_URLS=http://10.0.0.1:2380
ETCD_LISTEN_CLIENT_URLS=http://10.0.0.1:2379,http://127.0.0.1:2379
ETCD_INITIAL_ADVERTISE_PEER_URLS=http://10.0.0.1:2380
ETCD_ADVERTISE_CLIENT_URLS=http://10.0.0.1:2379
ETCD_INITIAL_CLUSTER=m1=http://10.0.0.1:2380,m2=http://10.0.0.2:2380,w=http://10.0.0.3:2380
ETCD_INITIAL_CLUSTER_STATE=new
ETCD_INITIAL_CLUSTER_TOKEN=x-ui
```

Порты 2379/2380 открывать только между этими тремя машинами (WireGuard между
ними или фаервол по IP).

### 2. PostgreSQL + Patroni на `m1` и `m2`

```bash
apt install -y postgresql patroni
systemctl disable --now postgresql   # базой управляет Patroni
```

`/etc/patroni/config.yml` на `m1` (на `m2`: `name: m2` и адрес `10.0.0.2`):

```yaml
scope: x-ui
name: m1
etcd3:
  hosts: 10.0.0.1:2379,10.0.0.2:2379,10.0.0.3:2379
restapi:
  listen: 10.0.0.1:8008
  connect_address: 10.0.0.1:8008
bootstrap:
  dcs:
    ttl: 30
    loop_wait: 10
    maximum_lag_on_failover: 1048576
    postgresql:
      use_pg_rewind: true
  initdb: [{ encoding: UTF8 }, data-checksums]
  pg_hba:
    - host replication replicator 10.0.0.0/24 scram-sha-256
    - host all all 10.0.0.0/24 scram-sha-256
    - host all all 127.0.0.1/32 scram-sha-256
postgresql:
  listen: 0.0.0.0:5432
  connect_address: 10.0.0.1:5432
  data_dir: /var/lib/postgresql/patroni
  bin_dir: /usr/lib/postgresql/17/bin   # своя версия PostgreSQL
  authentication:
    superuser: { username: postgres, password: "<пароль>" }
    replication: { username: replicator, password: "<пароль>" }
```

```bash
systemctl enable --now patroni      # сначала на m1, потом на m2
patronictl -c /etc/patroni/config.yml list
```

Базу и пользователя для панели создать один раз на текущем лидере:

```bash
sudo -u postgres psql -h 10.0.0.1 -c "CREATE USER xui PASSWORD '<пароль>'" -c "CREATE DATABASE xui OWNER xui"
```

Patroni сам переключает базу на живую машину. Чтобы база вернулась на `m1`
после его восстановления, выполните `patronictl switchover --leader m2 --candidate m1`
(автоматический возврат базы Patroni не делает специально, чтобы не было
лишних переключений; главенство панели возвращается само, см. ниже).

### 3. Панель на `m1` и `m2`

`/etc/default/x-ui` на `m1`:

```bash
XUI_DB_TYPE=postgres
XUI_DB_DSN=postgres://xui:<пароль>@10.0.0.1:5432,10.0.0.2:5432/xui?sslmode=disable&target_session_attrs=read-write
XUI_MASTER_PRIORITY=1
XUI_MASTER_NAME=m1
XUI_MASTER_URL=https://10.0.0.1:2053
```

На `m2` то же самое, но `XUI_MASTER_PRIORITY=2`, `XUI_MASTER_NAME=m2`,
`XUI_MASTER_URL=https://10.0.0.2:2053`. `target_session_attrs=read-write`
заставляет панель всегда писать в текущую главную базу.

Как это работает:
- каждый мастер раз в 5 секунд пишет в общую базу сигнал «я жив» (время берётся
  с часов базы, поэтому расхождение часов мастеров не мешает);
- ведущим становится живой мастер с лучшим приоритетом. Если ведущий 20 секунд
  молчит, ведущим становится следующий. Вернувшийся главный мастер ждёт 30 секунд
  и забирает главенство обратно;
- только ведущий синхронизирует ноды, считает трафик нод, сбрасывает трафик по
  расписанию, держит закрепления каскадов, домашние сети, ограничения скорости,
  LDAP и запускает Telegram- и Discord-ботов. Остальные мастера работают как
  горячий резерв: раз в 30 секунд подтягивают общий конфиг Xray;
- при смене ведущего в Telegram приходит уведомление «Мастер … теперь ведущий»;
- список мастеров и их состояние видно на странице «Ноды» (карточка «Мастеры»)
  и командой `x-ui cluster status` (её нужно запускать с переменными из `/etc/default/x-ui`).

Ноды доверяют всем мастерам сами: токены нод и mTLS-сертификат мастера хранятся
в общей базе.

### 4. Один адрес панели и подписок (keepalived)

Плавающий IP `10.0.0.100` (или публичный, если хостер разрешает) держит тот
мастер, который сейчас ведущий:

```bash
apt install -y keepalived
```

`/etc/keepalived/keepalived.conf` на `m1` (на `m2`: `priority 100`):

```
vrrp_script xui_leader {
  script "/usr/local/x-ui/x-ui cluster is-leader"
  interval 2
  fall 2
  rise 2
}
vrrp_instance XUI {
  interface eth0
  virtual_router_id 51
  priority 110
  advert_int 1
  virtual_ipaddress { 10.0.0.100/24 }
  track_script {
    xui_leader weight -50
  }
}
```

`x-ui cluster is-leader` не ходит в базу: он читает файл роли, который панель
обновляет при каждом сигнале, и отвечает «нет», если файл старше 15 секунд.
Если плавающий IP невозможен, DNS-запись панели и подписок с TTL 30–60 секунд
переключается на адрес ведущего мастера вручную или скриптом с той же проверкой.

## Сборка

```bash
cd frontend && npm ci && npm run build && cd ..
go build -o x-ui .
```

Нужны Go 1.27+ и Node.js 26+ (`npm` 11+).
